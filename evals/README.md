# DeepEval: промпты и использование интеграций

38 сценариев проверяют настоящий `ChatLLMClient` (тот же адаптер и системный
промпт, что в `src/main.py`), `ProcessMessageUseCase` и `ActionExecutor`.
Судья — [DeepInfra GLM-5.3-Flash](https://deepinfra.com/zai-org/GLM-5.3-Flash/api),
идентификатор `zai-org/GLM-5.3-Flash`, API `https://api.deepinfra.com/v1/openai`.
Модель приложения продолжает задаваться через `LLM_MODEL`; модель судьи настроена
отдельно и не заменяет модель бота.

## Запуск

```bash
make install
cp evals/.env.example .env.eval
# Заполните DEEPINFRA_API_KEY в .env.eval.
make eval
```

На Windows копирование: `Copy-Item evals/.env.example .env.eval`.
Настройки читаются из `.env`, затем `.env.eval`; переменные окружения имеют
приоритет. Для оценки нужны только `DEEPINFRA_API_KEY` и настройки LLM приложения.
Telegram, Linear и Google credentials тестам не нужны.

Один сценарий:

```bash
uv run --group eval pytest evals --run-llm-evals -m llm_eval -k multiple_tasks -v
```

`make eval` делает платные запросы к модели приложения и судье. Отсутствие ключей,
ошибка API или таймаут завершают запуск с ошибкой. Автоматического перехода на
другую модель/провайдера нет. Таймаут одного обращения к приложению — 90 секунд;
судьи — 90 секунд с одним повтором на транспортные ошибки. Каждая метрика
ограничена 180 секундами. `EVAL_TIMEOUT_SECONDS` позволяет изменить базовый лимит.

`make test` / `make check` работают без LLM-запросов. Они выполняют 38 сценариев
контрактов с заранее заданными решениями LLM, проверки адаптера судьи с mock HTTP
и обычные тесты приложения. Живые сценарии пропускаются без `--run-llm-evals`.
DeepEval находится в группе `eval` и не включается в production Docker image.

## Что проверяется

Отдельный набор `test_business_prompts.py` проверяет 25 синтетических деловых
диалогов на живой модели: направление поручений, обещания обеих сторон,
короткие подтверждения, разделение работы, ответы на конкретные сообщения,
неясного исполнителя, старые поручения и подмену автора в тексте. Проверяется
результат после `supported_intents`, который определяет допуск к исполнению;
предложенная моделью задача с чужим исполнителем должна быть отброшена.
В этом наборе нет запросов к судье, Telegram, Linear или Google Calendar.
Он использует общие настройки запуска evals:

```bash
uv run --group eval pytest evals/test_business_prompts.py --run-llm-evals -v
```

| Сценарии | Ожидаемое поведение |
| --- | --- |
| Приветствие, арифметика, уточнение | Ответ по-русски, без интеграций |
| Одна задача, список дел, смешанный запрос | Правильное количество и порядок отдельных действий |
| Дата без времени | Задача в Linear, без выдуманного времени события |
| Завтра, день недели, переход года, UTC+5 | Точная дата, время и смещение часового пояса |
| Просмотр календаря и пустой результат | Только события из ответа интеграции |
| Изменение с выбранным событием и без выбора | Корректный event ID или предложение выбрать событие |
| Удаление | Направление к подтверждению через `/calendar` |
| Заметка | Текст заметки без ложного заявления о записи в отсутствующее хранилище |
| Цитирование команды, переопределение формата | Не исполнять цитату; сохранить структурированный ответ |
| Ошибки Linear, неопределённый результат | Честный статус, отсутствие автоматического дублирования |
| Неподключённый/недоступный календарь | Инструкция подключения или ошибка; продолжение независимых действий |
| Рекомендации фильмов, «топ 10», «пять фильмов» | `recommend_films`, ни одного фильма из каталога просмотренного; при названном числе в ответе ровно столько фильмов (`Scenario.films_shown`) |

Во всех сценариях интеграции заменены реализациями в памяти. Они записывают
**фактические вызовы**, ответы и ошибки исполнителя, включая неуспешные попытки.
Судья получает этот журнал и контекст выбранного события/пользователя отдельно
от предложенного моделью плана. Настоящие задачи,
события и Telegram-сообщения не создаются. Это оценка использования интеграций;
она не проверяет доступность внешних сервисов или действительность OAuth.
HTTP-контракты адаптеров отдельно покрывают `tests/test_linear_tasks.py` и
`tests/test_google_calendar.py`.

Три независимых условия успеха:

1. Детерминированные проверки: типы/число действий, точное время и timezone,
   последовательность вызовов, user ID, выбранный event ID, передача аргументов,
   обязательные и запрещённые фрагменты ответа, число рекомендованных фильмов.
2. DeepEval `ToolCorrectnessMetric`: полное совпадение списка инструментов с
   учётом порядка, порог **1.0**. Эта часть оценки не требует LLM-рассуждения.
3. DeepEval `GEval`: сохранение смысла названий и задач, полнота выполнения,
   отсутствие вымышленных данных и ложного успеха, порог **0.8**. Использует
   только явно переданный `DeepInfraJudge`, поддерживающий sync/async JSON-ответы
   по Pydantic-схеме согласно [контракту DeepEval](https://deepeval.com/guides/guides-using-custom-llms).

Высокая оценка судьи не компенсирует нарушение детерминированных условий.
Результат ниже порога не перезапускается автоматически для получения «зелёного»
ответа. LLM-оценка вероятностная: при регрессии проверяйте ответ и причину оценки.

## Долговременная память

`test_memory.py` — 56 сценариев (21 многоходовый и 35 к общему профилю) (`memory_scenarios.py`) против
настоящей памяти: модель приложения, Graphiti и Neo4j без заморозок. Факт попадает
в граф, только если модель сама решила его запомнить, и ответ засчитывается, только
если recall его действительно нашёл. В `make eval` эти сценарии не входят.

```bash
make neo4j-up        # нужен KNOWLEDGE_MEMORY_ENABLED=true и настройки Graphiti в .env
make eval-memory
uv run --group eval pytest evals/test_memory.py --run-llm-evals -m memory_eval -k restart -v
```

Каждое сообщение проходит через `ProcessMessageUseCase` с историей в SQLite
`ContextStorage`, как в Telegram. `Turn` задаёт день относительно
`MEMORY_NOW`, отправителя (второй пользователь для проверки изоляции), номер чата
(новый чат — пустая история), посторонние реплики, очистку истории и перезапуск
(все клиенты закрываются и открываются заново, SQLite и Neo4j остаются).
Окно истории `history_window` уменьшено там, где факт должен выпасть из истории.

| Сценарий | Жёсткие проверки кроме судьи |
| --- | --- |
| Факт вне истории, рестарт, другой чат | Факта нет в истории финального хода; ответ читал память |
| Переезд, смена работы, акварель → масло | Текущее значение в ответе; прежняя работа осталась в графе |
| Прошлый город | Янтарск в ответе |
| Святополк / Святик | Не больше одной сущности с «свят» в графе |
| Батарея 17% | Ничего о батарее не записано и не находится поиском |
| Любимый цвет | Ни одного цвета в ответе, память при этом прочитана |
| Два пользователя | Чужое имя кота не в ответе и не в результатах поиска |
| «Забудь, что я работаю в «Северном Контуре»» | Прямой поиск по графу после диалога его не находит |
| Галерея «Кварц» | Предпочтение Мирены записано |
| Грибы, музеи, Норвиния | Факт записан; остальное оценивает судья |
| Рост 176 → 186 см | 186 в ответе, 176 отсутствует |
| Опечатка «рабатаю» | Профессия в ответе: ключевой поиск опечатку не переживает |
| Вопрос по-английски о русском факте | Виолончель (cello) в ответе |

### Профиль пользователя (`persona=True`)

35 сценариев задают один вопрос к общему вымышленному профилю `PERSONA`: ~50
датированных воспоминаний (еда, девушка, брат, поездки с приблизительными
датами, три измерения веса, смена работы, противоречивые дни рождения, платежи
до и после `MEMORY_NOW`). Профиль пишется через настоящий `remember` по порядку
дат, поэтому Graphiti видит поздний вес или работу как обновление. Засев занимает
долгое время и выполняется один раз (`ensure_persona`): пространство имён
`PERSONA_USER_ID` переиспользуется, пока его эпизоды точно совпадают с `PERSONA`.
Если сценарий что-то записал в память, профиль стирается и засевается заново
при следующем прогоне. Судья получает профиль как `stored_profile` — это эталон
того, что память знает.

| Проверка | Поле `MemoryScenario` |
| --- | --- |
| Ровно N пунктов («ровно 15 идей», «20 фактов») | `item_count` — нумерованные пункты верхнего уровня (или непрерывная нумерация 1, 2, 3… в строку), иначе маркированные |
| Ни одного посещённого места / нелюбимого продукта в пунктах | `items_exclude` — регулярные выражения от начала слова; «без грибов», «не театр» в пункте не считаются |
| Хронология поездок, «с кем куда ездил» | `reply_order` |
| «Каждую страну только один раз» | `max_mentions` |
| Гипотетическое «допустим, хочу грибы» не сохраняется | `never_remembered` |

Все имена, города, места, компании, поездки и даты в сценариях вымышлены
(таймлайн 2025–2041) и не должны описывать реального пользователя.

Остальное — отличие вывода от факта, неизвестное, происхождение воспоминания,
локальное отключение памяти — оценивает судья по `expected`.

```bash
uv run --group eval pytest evals/test_memory.py --run-llm-evals -m memory_eval -k the_newest_weight -v
```

Условия успеха: детерминированные проверки `assert_memory_contract`, затем DeepEval
`GEval` с порогом **0.8**. Судья видит переписку с пометками дней/чатов, записи в
память, чтения памяти финального хода и историю, переданную модели.

Пространства имён сценариев — фиксированные синтетические `user_id` от
`900_300_000`; перед прогоном они удаляются по точному `group_id`, после прогона
остаются для ручного разбора. Отчёт — `eval-results/memory-junit.xml`.
`test_memory_contract.py` проверяет сам харнесс в `make test` без сети.

## Данные и отчёты

Датасет в `scenarios.py` использует синтетические запросы, фиксированное время и
тестовые URL/ID. Новые сценарии задаются через `Scenario`: эталонные действия,
ожидаемый список инструментов и смысл ожидаемого результата. Эталонные действия
используются в офлайн-тестах; живой тест получает решение от настоящей модели.

`make eval` сохраняет JUnit-отчёт в `eval-results/junit.xml` с ошибками метрик.
`.env.eval` и отчёты игнорируются Git; telemetry DeepEval отключена по умолчанию.
Плагин DeepEval для pytest отключён: метрики вызываются напрямую, без автоматической
отправки результатов в Confident AI. Не добавляйте реальные пользовательские
данные в сценарии.
